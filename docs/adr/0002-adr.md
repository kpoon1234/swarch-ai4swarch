# ADR-0002: ใช้ RabbitMQ แยกงานหลังสั่งซื้อออกจาก checkout

- **Status:** Proposed
- **Date:** 2026-10-22
- **Deciders:** ยังไม่ระบุผู้ตัดสินใจในหลักฐานที่ให้มา

## Context and problem

R-12 ต้องเปลี่ยนการส่งอีเมลยืนยันเป็น MailFast เพิ่มคะแนนผ่าน `loyaltyservice` และบันทึกเหตุการณ์สั่งซื้อสำหรับการตลาด โดยคาดว่าจะเพิ่ม SMS, fraud scoring และการปรับ recommendations ในปีหน้า (`docs/scenario.md:7–14`; requirement ของงานนี้)

| ข้อเท็จจริง | หลักฐาน |
|---|---|
| `PlaceOrder` เรียกชำระเงิน แล้วจัดส่ง ล้างตะกร้า สร้างผลลัพธ์ และรอส่งอีเมลก่อนตอบกลับ; หากอีเมลล้มเหลวจะบันทึกคำเตือนและยังตอบสำเร็จ | `system/online-boutique/src/checkoutservice/main.go:252–279` (`PlaceOrder`) |
| การชำระเงิน จัดส่ง และอีเมลเรียกผ่าน gRPC | `system/online-boutique/src/checkoutservice/main.go:369–393` (`chargeCard`, `sendOrderConfirmation`, `shipOrder`) |
| p95 ของ `PlaceOrder` ต้อง ≤ 500 ms; ปัจจุบันประมาณ 300 ms; โหลดสูงสุด 200 orders/s | `docs/scenario.md:24–25` |
| MailFast มี p95 1.5 s, p99 8 s, ล้มเหลวประมาณ 0.5% และจำกัด 50 emails/s | `docs/scenario.md:26` |
| คะแนนต้องเข้าภายใน 1 นาทีและไม่ซ้ำ; ออเดอร์ต้องไม่ล้มเหลวเพราะอีเมล คะแนน หรือ analytics ใช้งานไม่ได้ | `docs/scenario.md:27–28` |
| ทีมมี 4 คน ถนัด Go/gRPC; 2 คนเคยใช้ RabbitMQ; ใช้ Kubernetes และต้องการ open-source ที่ดูแลเอง | `docs/scenario.md:29–30` |

**[Inferred]** การรอ MailFast ใน checkout เสี่ยงเกินงบ latency จากเวลาที่ให้มา แต่ยังคำนวณ p95 รวมด้วยการบวก p95 ไม่ได้ (`docs/scenario.md:24,26`) หากส่งหนึ่งอีเมลต่อออเดอร์ที่ 200 orders/s ต่อเนื่อง คิวจะโตอย่างน้อย 150 รายการ/s ก่อนนับ retry; เพิ่ม worker อย่างเดียวแก้เพดานผู้ให้บริการไม่ได้ (`docs/scenario.md:25–26`)

ใน `PlaceOrder` ที่อ่าน ไม่พบการบันทึกออเดอร์ถาวรหรือ outbox และสร้าง UUID ใหม่ทุกคำขอ (`system/online-boutique/src/checkoutservice/main.go:230–280`) จึงยังอ้างการรับประกัน event หรือการป้องกันออเดอร์ซ้ำเมื่อผู้เรียก retry ไม่ได้ ส่วน Redis ใน ADR-0001 ใช้กับตะกร้าและยอมรับการสูญหายได้ จึงไม่ใช่หลักฐานว่ามีที่เก็บออเดอร์ทนทานแล้ว (`docs/adr/0001-use-redis-for-cart-storage.md:11,20,44–45`)

## Decision drivers

1. **ความพร้อมใช้งาน:** งานหลังสั่งซื้อขัดข้องต้องไม่ทำให้ออเดอร์ล้มเหลว (`docs/scenario.md:28`)
2. **ประสิทธิภาพและการรองรับโหลด:** checkout p95 ≤ 500 ms ที่ 200 orders/s โดยรองรับข้อจำกัด MailFast (`docs/scenario.md:24–26`)
3. **ความถูกต้อง:** คะแนนเข้าภายใน 1 นาทีโดยไม่มีคะแนนซ้ำ (`docs/scenario.md:27`)
4. **ความสามารถในการปรับเปลี่ยน:** เพิ่มงานหลังสั่งซื้อในปีหน้าได้สะดวก (`docs/scenario.md:14`)
5. **ต้นทุนและความง่ายในการดูแล:** เหมาะกับทีม 4 คน ประสบการณ์ RabbitMQ และ Kubernetes ที่มีอยู่ (`docs/scenario.md:29–30`)

## Considered options

1. ให้ `checkoutservice` เรียกอีเมล คะแนน และ analytics โดยตรงแบบ synchronous
2. ใช้ตัวประสานงานกลางแบบ asynchronous ซึ่งเก็บรายการงานถาวรและเรียกปลายทางแต่ละแห่ง
3. ใช้ RabbitMQ แบบ publish/subscribe โดยแยกคิวและผู้ประมวลผลแต่ละงาน พร้อม durable outbox

### Pros and cons of the options

ตารางเป็นการประเมิน **[Inferred]** ของทางเลือกใหม่ตามเป้าหมายใน `docs/scenario.md:14,24–30` ไม่ใช่คำอธิบายระบบที่ติดตั้งอยู่แล้ว

| Option | Pros | Cons |
|---|---|---|
| 1. เรียกโดยตรง | ใช้รูปแบบที่ทีมถนัด; ติดตามลำดับการทำงานง่าย | การรอ MailFast เสี่ยงเกิน latency; งานใหม่เพิ่ม dependency ของ checkout; การละเลยข้อผิดพลาดไม่ทำให้งานถูกทำครบและยังต้องมีกลไก retry ถาวร |
| 2. ตัวประสานงานกลาง | แยกเวลาทำงานจาก checkout; รวมสถานะและ retry ไว้จุดเดียว; ใช้ Go/gRPC ได้ | งานใหม่ต้องแก้ตัวประสานงาน; ต้องสร้างกลไกจัดคิวและกู้คืนเอง; ต้องป้องกันอีเมลค้างขวางคะแนนและ analytics |
| 3. RabbitMQ และผู้รับแยกคิว | เพิ่มงานด้วยผู้รับใหม่; แยกงานค้างและ retry ต่อประเภท; สอดคล้องกับประสบการณ์บางส่วนของทีม | เพิ่ม broker และที่เก็บถาวรที่ต้องดูแล; ต้องจัดการข้อความซ้ำและ schema; broker อย่างเดียวไม่แก้ช่องว่างระหว่างออเดอร์สำเร็จกับการส่ง event |

## Decision

เลือก **ทางเลือก 3** เพื่อแยก latency และความขัดข้องของงานหลังสั่งซื้อ และรองรับงานใหม่ (`docs/scenario.md:14,24–30`) รายละเอียดต่อไปนี้เป็น **ข้อเสนอใหม่** ยังไม่ใช่ความสามารถที่ยืนยันจากโค้ดปัจจุบัน

1. **บันทึกออเดอร์และ event:** หลังชำระเงินและจัดส่งสำเร็จ ให้บันทึกสถานะออเดอร์สำเร็จกับ `OrderPlaced.v1` ใน outbox ภายใน transaction เดียวของที่เก็บถาวรใหม่ ก่อนตอบ checkout สำเร็จ ย้ายการล้างตะกร้าไปหลังการบันทึกนี้; checkout ไม่รอ RabbitMQ หรือผู้ประมวลผลงาน ชนิดที่เก็บและการกู้คืนยังต้องตกลงใน **Open questions** (จุดปรับเดิม: `system/online-boutique/src/checkoutservice/main.go:252–279`)
2. **ส่ง event แบบกู้คืนได้:** relay ส่ง outbox เข้า RabbitMQ และทำเครื่องหมายส่งแล้วเมื่อได้รับ publisher confirmation; ใช้ exchange และคิวแบบ durable ข้อความ persistent และคิวที่ทำ replication เช่น quorum queues แยกคิวอีเมล คะแนน และ analytics ให้ผู้รับ acknowledge หลังบันทึกผลถาวรสำเร็จ และรองรับการส่งซ้ำเมื่อ relay หรือผู้รับล่มระหว่างขั้นตอน และต้องเพิ่ม Idempotency และ Reconciliation เผื่อในกรณีที่ บาง service สำเร็จและบาง service พัง
3. **สัญญาข้อมูล:** กำหนด `event_id`, `order_id`, `occurred_at`, รุ่น schema และข้อมูลขั้นต่ำสำหรับผู้รับ เช่น อีเมล รายการสั่งซื้อ ยอดเงิน สกุลเงิน และรหัสผู้ใช้ โดยไม่ส่งข้อมูลบัตรเครดิต ใช้ event เดิมตลอดการ retry และหนึ่งเหตุการณ์ต่อออเดอร์ ต้องเพิ่มกลไกผูกคำขอซ้ำกับออเดอร์เดิม เพราะปัจจุบันสร้าง UUID ใหม่ทุกครั้ง (`system/online-boutique/src/checkoutservice/main.go:233–236,243–252,265–271`)
4. **อีเมล:** เปลี่ยน mock logic ของ `emailservice` ให้เป็นผู้รับจากคิวและตัวเชื่อม MailFast ตาม R-12 (`docs/scenario.md:10`) ยกเลิกการเรียกอีเมลโดยตรงจาก checkout ที่ `system/online-boutique/src/checkoutservice/main.go:273–277,379–383` จำกัดอัตรารวมทุก replica ไม่เกิน 200 calls/s รวม retry; ใช้ timeout และ retry แบบ backoff พร้อม jitter งานที่ผิดพลาดถาวรหรือเกินเกณฑ์ retry ให้เข้าคิวพักตรวจสอบและแจ้งเตือน การป้องกันอีเมลซ้ำเมื่อ timeout ยังขึ้นกับความสามารถ MailFast ที่ไม่ทราบ
5. **คะแนน:** ให้ `loyaltyservice` รับคิวของตนเอง ใช้ `order_id` เป็น unique key และบันทึกคะแนนกับรายการประมวลผลใน transaction เดียว แล้วจึง acknowledge การส่งซ้ำต้องไม่เพิ่มคะแนนอีก เป้าหมายคือผลทางธุรกิจเกิดครั้งเดียวบนการส่งแบบ at-least-once ไม่อ้างว่า broker รับประกัน exactly-once ให้เอง (`docs/scenario.md:11,27`)
6. **Analytics และงานเพิ่ม:** ให้ผู้รับ analytics บันทึกเหตุการณ์ถาวรและป้องกันซ้ำด้วย `event_id` ก่อน acknowledge; ปลายทางจัดเก็บยังต้องกำหนด งานปีหน้าเพิ่มผู้รับและคิวของตนเองเมื่อเป็นงานหลังสั่งซื้อตาม R-12 (`docs/scenario.md:12–14`)
7. **แยกความขัดข้อง:** เมื่อปลายทางหรือ broker หยุดทำงาน ให้เก็บงานค้างและส่งใหม่โดยไม่ย้อนผลออเดอร์ที่บันทึกสำเร็จแล้ว เฝ้าระวังอายุข้อความ พื้นที่ outbox/คิว และความล้มเหลว แยกทรัพยากรประมวลผลคะแนนจากอีเมลเพื่อรักษากรอบ 1 นาที (`docs/scenario.md:26–28`)

**ขอบเขตการรับประกัน:** transaction ของ outbox ไม่ครอบคลุมผลภายนอกจากการชำระเงินและจัดส่งที่เกิดก่อนจุดบันทึก (`system/online-boutique/src/checkoutservice/main.go:252–261`) ต้องออกแบบ idempotency และการกระทบยอดเมื่อ process ล่มหลังชำระเงินหรือจัดส่งแต่ก่อนบันทึกออเดอร์ การเพิ่ม outbox เพียงอย่างเดียวยังไม่แก้ช่องว่างนี้ครบ

**[Inferred]** หาก `loyaltyservice` ล่มเกิน 1 นาที จะรับประกันทั้งคะแนนเข้าภายใน 1 นาทีและออเดอร์สำเร็จโดยไม่มีเงื่อนไขไม่ได้ ต้องตกลงขอบเขต outage และแนวทางชดเชยก่อนยอมรับการออกแบบ (`docs/scenario.md:27–28`) ADR นี้จึงคงสถานะ Proposed

## Consequences

- **Positive:** checkout ไม่รอ MailFast หรือผู้รับอื่น ลดความเสี่ยงต่อ p95 และแยกความขัดข้อง แต่ยังต้องวัด latency หลังเพิ่มการบันทึกถาวร (คุณลักษณะคุณภาพ: ประสิทธิภาพและความพร้อมใช้งาน; `docs/scenario.md:24,26,28`)
- **Positive:** ผู้รับแยกคิวช่วยเพิ่มงานและปรับกำลังประมวลผลแต่ละงานได้อิสระ (คุณลักษณะคุณภาพ: ความสามารถในการปรับเปลี่ยนและขยายระบบ; `docs/scenario.md:14,25`)
- **Positive:** outbox และ transaction ป้องกันคะแนนซ้ำเป็นแนวทางกู้คืนงานและรักษาความถูกต้อง (คุณลักษณะคุณภาพ: ความทนทานและความถูกต้อง; `docs/scenario.md:27–28`)
- **Negative:** ผลอีเมล คะแนน และ analytics เกิดภายหลังออเดอร์สำเร็จ ต้องมีสถานะและเครื่องมือค้นหางานค้าง (คุณลักษณะคุณภาพ: ความสอดคล้องของข้อมูลและการสังเกตการณ์; ข้อแลกเปลี่ยนของการออกแบบที่เสนอ)
- **Negative:** เพิ่มภาระดูแล broker ที่เก็บถาวร replication การสำรองและกู้คืน สำหรับทีม 4 คน (คุณลักษณะคุณภาพ: ต้นทุนและความสามารถในการดูแล; `docs/scenario.md:29–30`)
- **Risks and mitigations:** คิวอีเมลโตเมื่อโหลดเกิน 50 emails/s; จำกัดอัตรารวม เฝ้าระวังอายุคิว และตกลงเวลารอหรือเพิ่ม quota (คุณลักษณะคุณภาพ: ความสามารถในการขยายระบบและเวลาตอบสนอง; `docs/scenario.md:25–26`)
- **Risks and mitigations:** ข้อความซ้ำอาจให้คะแนนซ้ำ; ใช้ unique key และ transaction เดียวสำหรับคะแนนกับสถานะประมวลผล พร้อมทดสอบ crash/replay (คุณลักษณะคุณภาพ: ความถูกต้อง; `docs/scenario.md:27`)
- **Risks and mitigations:** ที่เก็บออเดอร์/outbox เป็น dependency ใหม่ของการยืนยันออเดอร์ และ outage ยาวอาจทำให้พื้นที่เต็ม; วางแผน replication การกู้คืน ความจุ และนโยบายเมื่อเขียนไม่ได้ โดยยังต้องตกลงรายละเอียด (คุณลักษณะคุณภาพ: ความพร้อมใช้งานและความทนทาน; ความเสี่ยงของการออกแบบที่เสนอ)

| การตรวจสอบ | เกณฑ์และหลักฐานที่ต้องเก็บ |
|---|---|
| โหลด 200 orders/s พร้อมจำลอง MailFast p95 1.5 s, p99 8 s และล้มเหลวประมาณ 0.5% | `PlaceOrder` p95 ≤ 500 ms; อัตรารวมทุก replica ≤ 50 calls/s รวม retry; วัดการโตของคิว โดยต้องตกลงระยะเวลาโหลดสูงสุดก่อนกำหนดความจุ (`docs/scenario.md:24–26`) |

| ส่งซ้ำ ประมวลผลพร้อมกัน และบังคับล่มหลัง commit คะแนนแต่ก่อน acknowledge | แต่ละ `order_id` เพิ่มคะแนนครั้งเดียว รวม replay จากคิวพัก (`docs/scenario.md:27`) |
| บังคับล่มหลังชำระเงิน หลังจัดส่ง หลัง commit outbox และหลัง publish แต่ก่อนทำเครื่องหมายส่งแล้ว | ตรวจ event ครบและการกระทบยอด; คำขอ checkout ซ้ำต้องผูกกับออเดอร์เดิม ช่องว่างที่ยังแก้ไม่ได้ต้องบันทึกก่อนยอมรับ ADR (จุดเสี่ยง: `system/online-boutique/src/checkoutservice/main.go:233–279`) |

## Open questions

ข้อมูลที่ยังไม่มีด้านล่างถือเป็น “Not evidenced in the provided files” และต้องตอบก่อนยอมรับหรือกำหนดขอบเขตการรับประกัน

- ใครเป็นผู้ตัดสินใจ เจ้าของบริการ และผู้ดูแล broker กับที่เก็บถาวร?
- ออเดอร์สำเร็จ ณ จุดใด และใช้ที่เก็บใดบันทึกออเดอร์/outbox แบบ atomic? เป้าหมายเวลากู้คืนและปริมาณข้อมูลสูญหายที่ยอมรับได้คือเท่าใด?
- จะผูกคำขอ checkout ซ้ำกับออเดอร์เดิมอย่างไร? การชำระเงินและจัดส่งรองรับ idempotency หรือการตรวจผลเพื่อกระทบยอดหรือไม่? ทำอย่างไรเมื่อชำระเงินแล้วแต่บันทึกออเดอร์ไม่ได้?
- กรอบคะแนน 1 นาทีครอบคลุม outage แบบใด? ทำอย่างไรเมื่อบริการคะแนนล่มเกิน 1 นาที และกฎคำนวณคะแนนคืออะไร?
- ช่วง 200 orders/s ยาวเท่าใด? ยอมรับความล่าช้าอีเมลสูงสุดเท่าใด และ MailFast เพิ่ม quota ได้หรือไม่?
- MailFast ใช้ API/protocol และการยืนยันตัวตนแบบใด? รองรับ idempotency หรือค้นหาผลเมื่อ timeout หรือไม่ และนับ quota ของคำขอล้มเหลวอย่างไร?
- ปลายทางและ schema ของ analytics คืออะไร? ต้องเก็บข้อความและข้อมูลนานเท่าใด รวมถึงสิทธิ์เข้าถึงและนโยบายลบข้อมูลผู้รับอีเมล?
- ต้องกำหนดจำนวน replica ความจุ retention ระยะ retry เกณฑ์แจ้งเตือน และขั้นตอน replay เท่าใดจากผลทดสอบและทรัพยากรจริง?
- fraud scoring ปีหน้าเป็นงานหลังสั่งซื้อหรือใช้อนุมัติก่อนสั่งซื้อ? หากเป็นเงื่อนไขอนุมัติ ต้องพิจารณาขอบเขต ADR ใหม่ (`docs/scenario.md:14`)
